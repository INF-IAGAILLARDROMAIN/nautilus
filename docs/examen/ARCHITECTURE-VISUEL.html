👥 Qui agit sur quoi — vue acteur

Front Next.js

Affiche, valide, appelle

Rend les pages HTML, valide les formulaires avec Zod côté navigateur, envoie les requêtes au back avec le cookie JWT. Ne touche JAMAIS la BDD directement.

Back NestJS

Orchestre, sécurise, exécute

Vérifie le JWT, valide les DTO, parle aux BDD via Prisma/Mongoose, appelle Mistral pour la classification, génère les PDFs avec pdfkit. Le chef d'orchestre.

PostgreSQL (Neon)

Garde les données métier

Client, Bateau, Devis, OR + LigneDevis. ACID, relations fortes, intégrité référentielle. Ne dialogue qu'avec le back via Prisma.

MongoDB Atlas

Trace toutes les recherches IA

Un document par requête (question, intent, entities, temps, statut). Audit RGPD côté éditeur RANKIA. Schéma flexible car les entities varient par intent.

Supabase Auth

Signe et publie

Signe les JWT à la connexion (avec sa clé privée), publie la clé publique via JWKS. Le back vérifie sans connaître le secret. La clé privée ne quitte JAMAIS Supabase.

Mistral AI

Classifie les questions

Reçoit la question en français + le prompt système, renvoie un intent (parmi 23) + des entités extraites. AUCUN pouvoir d'écriture. AUCUN accès BDD. Juste un classifier intelligent.

🔄 Les 3 flows à mémoriser

Flow 1 — Authentification (qui parle à qui)

  1. L'utilisateur tape email + mot de passe sur la page login
  2. Le front envoie ces creds à Supabase
  3. Supabase vérifie, signe un JWT avec sa clé privée ES256
  4. Le front reçoit le JWT, le stocke dans un cookie httpOnly
  5. À chaque requête vers le back, le cookie est envoyé
  6. Le back récupère la clé publique Supabase via JWKS
  7. Le back vérifie la signature du JWT avec la clé publique
  8. Si valide → autorisé. Sinon → 401
Point fort : la clé privée ne quitte jamais Supabase. Si mon back est compromis, l'attaquant ne peut PAS forger de token.

Flow 2 — Création client + bateau (CRUD typique)

  1. L'utilisateur remplit le formulaire React Hook Form
  2. Zod valide les champs côté navigateur (UX immédiate)
  3. Si OK, le front envoie POST /api/clients avec le JWT
  4. NestJS reçoit, passe par le Guard JWT ES256 (auth ?)
  5. NestJS passe par le DTO + class-validator (données valides ?)
  6. NestJS appelle ClientsService → Prisma → PostgreSQL
  7. PostgreSQL crée la ligne, applique les CHECK / FOREIGN KEY
  8. NestJS renvoie le client créé en JSON
  9. Le front met à jour le cache TanStack Query, affiche la fiche
Défense en profondeur : si quelqu'un bypass le front, le DTO refuse. Si le DTO est bypass, Prisma refuse. Si Prisma est bypass, PostgreSQL refuse. Quatre étages.

Flow 3 — Recherche IA (le cœur du projet)

  1. L'utilisateur tape « le bateau de Martin »
  2. Le front envoie POST /api/recherche-ia { question }
  3. NestJS vérifie le JWT (Guard), valide le DTO
  4. Le service construit le prompt système + envoie à Mistral
  5. Mistral répond : { intent: "find_bateau", entities: { client_name: "Martin" } }
  6. Mon code switch sur l'intent → appelle Prisma avec un WHERE typé
  7. PostgreSQL renvoie les bateaux trouvés
  8. En parallèle : un log MongoDB est créé (userId, question, intent, entities, temps, statut)
  9. NestJS renvoie au front : { intent, results, messageInfo }
  10. Le front affiche le bandeau adaptatif + la liste des bateaux
Point fort : à AUCUN moment Mistral ne touche à la BDD. Il ne fait que classifier. La sécurité est par design, pas par filtre.

📚 Glossaire technique — tous les termes utilisés

Pour chaque acronyme : ce que ça veut dire, ce que ça fait, et où c'est dans Nautilus.

🔐 1. Authentification & Sécurité

JWT
JSON Web Token
Un petit fichier texte signé numériquement qui prouve qui tu es. Quand tu te connectes, Supabase t'en donne un, et le back le vérifie à chaque requête.
→ Stocké en cookie httpOnly, envoyé à chaque appel API
ES256
Elliptic Curve Signature 256 bits
Une méthode de signature asymétrique : une clé privée signe, une clé publique vérifie. C'est ultra-sécurisé.
→ Le format de signature des JWT Supabase
JWKS
JSON Web Key Set
Un endpoint web public qui expose la clé publique de Supabase. Mon back va la chercher pour vérifier les JWT.
→ Le mécanisme par lequel le back vérifie les tokens sans connaître le secret
httpOnly
(cookie)
Un cookie marqué httpOnly est invisible pour JavaScript. Donc même si une faille XSS existe, l'attaquant ne peut pas voler le JWT.
→ Tous mes cookies d'auth
CORS
Cross-Origin Resource Sharing
Une règle du navigateur qui empêche un site A d'appeler l'API du site B sans permission. Je liste explicitement les origines autorisées.
→ Configuré dans NestJS (n'accepte que vercel.app et localhost)
CSP
Content Security Policy
Un header HTTP qui dit au navigateur quels scripts, images et iframes il a le droit de charger. Bloque les injections de code malveillant.
→ Posé par Helmet sur toutes les réponses
HSTS
HTTP Strict Transport Security
Un header qui force le navigateur à toujours utiliser HTTPS, jamais HTTP. Anti man-in-the-middle.
→ Posé par Helmet
bcrypt
(algorithme de hash)
Une fonction qui transforme un mot de passe en un hash impossible à inverser. Même si ma BDD fuite, on ne récupère pas les mots de passe.
→ Utilisé par Supabase pour stocker les mots de passe
TLS
Transport Layer Security
Le protocole qui chiffre les communications entre ton navigateur et un serveur (c'est ce qui fait le « S » de HTTPS).
→ Activé par défaut sur Vercel et Railway
Guard
(NestJS)
Une fonction qui s'exécute avant ton code métier et qui dit « stop » si quelque chose ne va pas (token invalide, mauvais rôle…).
→ J'ai un SupabaseJwtGuard global sur toutes les routes protégées

⚙️ 2. Back-end (API, NestJS, données)

API
Application Programming Interface
Le mécanisme par lequel deux logiciels se parlent. Mon back expose une API REST que le front utilise.
→ https://nautilus-back.railway.app/api/*
REST
Representational State Transfer
Un style d'API standard : tu utilises les verbes HTTP (GET, POST, PATCH, DELETE) pour manipuler des ressources.
→ Mes endpoints suivent REST : GET /clients, POST /devis…
DTO
Data Transfer Object
Un objet TypeScript qui décrit la forme exacte d'une donnée entrante. Si un champ ne correspond pas, le back refuse la requête.
→ Tous mes endpoints ont un DTO avec class-validator
class-validator
(librairie NestJS)
Une bibliothèque qui lit les annotations sur mes DTO (@IsEmail(), @Length(2, 50)) et rejette toute requête malformée.
→ Sur tous mes DTO. C'est mon mur de validation côté back.
ORM
Object-Relational Mapper
Un outil qui me permet d'écrire des requêtes BDD en TypeScript au lieu de SQL brut. C'est plus sûr et plus lisible.
→ Prisma 6 pour PostgreSQL, Mongoose pour MongoDB
Throttler
(NestJS)
Un module qui limite le nombre de requêtes par IP. Si quelqu'un essaie de brute-force mon login, il est bloqué.
→ 100 req/min par IP en global
Helmet
(librairie sécurité)
Une bibliothèque qui ajoute automatiquement tous les bons headers HTTP de sécurité (CSP, HSTS, X-Frame-Options…).
→ Activée en début de pipeline NestJS
Module
(NestJS)
Une boîte qui regroupe Controller + Service + DTO autour d'un domaine métier. J'ai 9 modules métier dans Nautilus.
→ ClientsModule, DevisModule, RechercheIaModule…
Controller
(NestJS)
La classe qui reçoit les requêtes HTTP, déclare les routes et délègue le travail au Service. C'est la "porte d'entrée" du module.
→ Un par module métier : ClientsController, etc.
Service
(NestJS)
La classe qui contient la logique métier. Le Controller appelle le Service qui fait le vrai travail (calculs, accès BDD).
→ ClientsService.create(), DevisService.calculTVA()…

🎨 3. Front-end (Next.js, React)

SPA
Single Page Application
Une appli web où la navigation se fait sans recharger la page. Plus fluide qu'un site classique.
→ Nautilus est une SPA grâce à Next.js App Router
Server Component
(Next.js)
Un composant React rendu côté serveur avant d'être envoyé au navigateur. Plus rapide et plus sécurisé.
→ Toutes mes pages de liste et de détail
Client Component
(Next.js)
Un composant React rendu côté navigateur. Nécessaire pour l'interactivité (formulaires, animations).
→ Mes formulaires et la barre de recherche IA
App Router
(Next.js)
Le système de routes de Next.js 16 basé sur la structure des dossiers : app/dashboard/clients/page.tsx devient /dashboard/clients.
→ Toutes mes routes Nautilus suivent ce modèle
Zod
(librairie de validation)
Une bibliothèque TypeScript qui valide des données contre un schéma. Si le champ n'est pas valide, j'affiche une erreur dans le formulaire.
→ Tous mes formulaires React Hook Form
React Hook Form
(librairie React)
Gère l'état des formulaires de manière performante. Couplé à Zod, c'est le standard 2025 pour les formulaires React.
→ Création client, bateau, devis, etc.
TanStack Query
(ex React Query)
Une bibliothèque qui met en cache les requêtes API et les rafraîchit intelligemment. Évite les appels inutiles.
→ Toutes mes requêtes vers l'API back
CDN
Content Delivery Network
Un réseau de serveurs distribués mondialement qui servent les fichiers au plus près de l'utilisateur. Très rapide.
→ Vercel fournit le CDN edge automatiquement
Tailwind CSS
(framework CSS)
Un système de classes utilitaires (bg-blue-500, p-4) qui me permet de styliser sans écrire de CSS.
→ Tout le style de Nautilus en Tailwind v4
XSS
Cross-Site Scripting
Une attaque où un attaquant injecte du JavaScript malveillant dans une page. Cookies httpOnly + CSP me protègent.
→ Risque OWASP A03 traité par design

🗄 4. Bases de données

PostgreSQL
(BDD relationnelle)
La base de données la plus solide du marché open source. Stocke des données en tables avec des relations entre elles.
→ Hébergée chez Neon, Frankfurt
MongoDB
(BDD documentaire)
Une base NoSQL qui stocke des documents JSON. Très flexible : pas besoin de schéma rigide.
→ Hébergée chez Atlas, Paris. Stocke les logs IA.
ACID
Atomicity, Consistency, Isolation, Durability
Les 4 garanties d'une BDD relationnelle : tes transactions sont fiables, même en cas de crash. PostgreSQL est ACID.
→ Garantit que la création devis + OR + ligne fonctionne ou échoue ensemble
SQL
Structured Query Language
Le langage standard pour interroger une BDD relationnelle. Mais je n'écris pas de SQL à la main — Prisma le génère pour moi.
→ Généré automatiquement par Prisma
NoSQL
Not Only SQL
Les BDD qui ne suivent pas le modèle relationnel. Plus flexibles, mais moins de garanties que SQL.
→ MongoDB pour mes logs IA
CRUD
Create, Read, Update, Delete
Les 4 opérations de base sur une donnée. Mes formulaires Nautilus font tous du CRUD.
→ POST (create), GET (read), PATCH (update), DELETE
Migration
(Prisma)
Un fichier SQL généré quand je modifie le schéma. Permet de versionner l'évolution de la BDD comme du code.
→ Dossier backend/prisma/migrations/
Foreign Key
Clé étrangère SQL
Un lien qui dit « ce bateau appartient à ce client ». Si je supprime le client, je peux automatiquement supprimer ses bateaux (cascade).
→ Client → Bateau, Bateau → Devis, etc.
Index
(BDD)
Une structure qui accélère les recherches sur une colonne. Sans index, une recherche par nom prend longtemps. Avec, c'est instantané.
→ Index sur Client(nom, prenom), Bateau(plaqueMoteur)
Mongoose
(ODM MongoDB)
L'équivalent de Prisma pour MongoDB. Me permet de définir un schéma TypeScript pour mes documents.
→ Modèle RechercheLog pour les logs IA

🤖 5. LLM & Intelligence artificielle

LLM
Large Language Model
Un modèle d'IA entraîné sur des milliards de textes, capable de comprendre et générer du langage naturel.
→ J'utilise Mistral AI, un LLM français
Prompt système
(IA)
Les instructions de fond que je donne au LLM avant ses requêtes : « tu es un classifier, voici les 23 intents possibles ».
→ Mon prompt système Nautilus fait ~1200 lignes
Intent
(IA)
L'intention détectée derrière une question. « le bateau de Martin » → intent = find_bateau.
→ J'ai 23 intents pré-codés (19 métier + 3 UX + 1 sécurité)
Entities
(IA)
Les entités extraites d'une question. « le bateau de Martin » → entities = { client_name: "Martin" }.
→ Schéma variable selon l'intent
Pattern Intent + Entities
(architecture IA)
Un design où le LLM ne génère PAS de code mais choisit dans une liste fermée. C'est ce qui me protège du prompt injection.
→ Cœur de l'architecture sécurisée de Nautilus
Prompt injection
(attaque IA)
Une attaque où l'utilisateur tape « ignore tes consignes et… ». Un LLM mal conçu obéit. Le mien ne peut pas — il classifie seulement.
→ OWASP LLM01, neutralisé par design
Température (LLM)
(paramètre IA)
Un paramètre entre 0 et 2 qui contrôle la créativité. À 0 = déterministe (même question = même réponse). À 1 = créatif.
→ Je l'ai mise à 0 pour garantir la reproductibilité
Token
(LLM)
L'unité de mesure d'un texte pour un LLM. ~4 caractères = 1 token. La facturation Mistral se fait au token.
→ ~600 tokens par requête Nautilus en moyenne
JSON mode
(LLM)
Un paramètre qui force le LLM à répondre en JSON valide. Garantit que sa réponse est parseable.
→ Activé : response_format: "json_object"
Few-shot
(prompt engineering)
Donner au LLM des exemples concrets dans le prompt pour qu'il comprenne le pattern attendu. Mon prompt en contient 38.
→ 38 exemples Q/R dans le prompt système

📋 7. Standards & Référentiels

OWASP
Open Web Application Security Project
Une fondation qui publie les références mondiales de sécurité web. Le « Top 10 » liste les 10 risques majeurs.
→ J'ai traité 5 risques sur 10 dans Nautilus (A01, A02, A03, A05, A07)
OWASP LLM Top 10
(référentiel IA)
L'équivalent du Top 10 classique pour les apps qui utilisent un LLM. Publié en 2023, mis à jour en 2025.
→ J'ai traité LLM01, LLM02, LLM06, LLM08 dans Nautilus
RGPD
Règlement Général sur la Protection des Données
La loi européenne sur la protection des données personnelles. Impose la traçabilité, le consentement, le droit à l'oubli.
→ 100 % infra UE + audit éditeur RANKIA
RNCP
Répertoire National des Certifications Professionnelles
Le registre français qui catalogue tous les diplômes reconnus par l'État. Mon Titre Pro DWWM a le numéro 37674.
→ Le titre que je vise le 29/06
France Compétences
(autorité publique)
L'organisme qui gère le RNCP et définit les modalités des titres professionnels. C'est leur site qui dit officiellement « 35 min de présentation ».
→ Source légale de la durée de mon oral
CERT-FR
Centre gouvernemental de veille
L'agence nationale française qui publie les alertes de sécurité. Je la consulte dans ma veille hebdo.
→ Une de mes 4 sources de veille
ACID (rappel)
Atomicity, Consistency, Isolation, Durability
Garanties d'une BDD relationnelle. PostgreSQL est ACID, MongoDB ne l'est pas (par design).
→ PostgreSQL me garantit que mes transactions métier sont fiables
DREETS
Direction Régionale, de l'Économie, de l'Emploi, du Travail et des Solidarités
L'administration française qui valide et délivre officiellement le Titre Pro après ton examen.
→ C'est la DREETS qui me donnera mon diplôme

🎯 Quelle question piège attendre du jury

Le jury Studi est composé d'un formateur et d'un pro du métier. Voici les 5 questions techniques les plus probables, avec la réponse-type :

Question piège Réponse-type
« Pourquoi pas une seule BDD ? » Le référentiel exige SQL ET NoSQL. J'ai trouvé un cas d'usage légitime pour MongoDB (logs IA semi-structurés) plutôt qu'un cas artificiel.
« Pourquoi vous ne stockez pas les PDF ? » Choix volontaire. Régénération à la demande = toujours à jour. Pas de stockage objet à gérer. Le PDF est un format de sortie, pas de stockage.
« Et si Mistral est down ? » Le service catch l'erreur, logue en MongoDB, renvoie un message clair. Le reste de l'app continue de fonctionner. Dégradé gracieux.
« Pourquoi pas du SSR sur les pages détail ? » J'utilise des Server Components Next.js qui rendent côté serveur APRÈS vérification d'auth. C'est plus sécurisé que du Client Component pur.
« Qu'est-ce qui empêche un utilisateur d'injecter du SQL via la recherche IA ? » Le pattern Intent + Entities. Le LLM ne génère AUCUN SQL — il choisit dans 23 intents pré-codés. C'est mon code Prisma typé qui exécute. Risque verrouillé par design.
